11. The stack, and why

Part three is about how this gets built. It starts with the language, because one live bug settles that argument better than any amount of principle: today the product's core signal reads as an honest zero for every TikTok post, and nothing in the codebase was capable of noticing.

The bug that answers the language question

The usual case against JavaScript is "it lets you make mistakes." True, and not good enough. The current build is 164 files and 25,776 lines of working JavaScript that does real work every day. Nobody is struggling to write it.

The real problem is narrower and much worse. This system is built on promises about shape — an adapter must hand core our vocabulary, not the vendor's — and in plain JavaScript there is no way to make a shape mandatory. It can only be described in a comment. Here is what that costs, in the file that reads TikTok posts.

TikTok has no quote-post. The parser hardcodes quotes = 0 because there is nothing to put there. Downstream, quotes is the reproduction count — other people making their own version — and it is the single strongest thing this product looks for. Every TikTok post therefore arrives looking uncopied. Nothing objected, because there was no shape to object to.

The 890K views on the harbour clip are real; so are the shares. The zero is not a wrong number, it is a category error wearing a number's clothes — and a category error is invisible to a reviewer scanning a file, because every line in it looks correct on its own.

What types actually buy

A contract is a plug shape. Right now the system has plug shapes drawn on paper next to each socket, and everyone agrees they should match. Occasionally someone plugs in the wrong thing, it fits physically, and the appliance runs slightly wrong for six months. Types make the plug shapes physical. The wrong adapter does not fit. You find out while you are holding it, not in a report three weeks later.

Under the new shape, an adapter has to declare what its platform cannot count. TikTok's adapter says "reproduction: absent" — not zero, absent — and core switches to deriving copies from the fingerprint index instead. You cannot ship an adapter that quietly claims a counter it does not have, because the declaration is required to build the object at all. The same move fixes two other promises this architecture is resting on:

Replay — "re-run every past decision under a new rule and see what changes" — is the reason the whole system is worth building. It only holds if deciding is pure. In JavaScript that is a promise; in TypeScript it is a shape the compiler will not let you break.

What runs where

Four boxes and one database. The important detail is the dotted one: Python is in the repository and never in production. It reads a table of numbers the system already wrote down at decision time, and hands back a model file. If Python vanished from the laptop at three in the morning, the system would keep making decisions with the file it already has.

The whole running system
three hosts, one database, and a laptop on Sundays
The usual reason to keep training and serving in one language is that the two drift apart. They cannot here: the trainer is not allowed to recompute anything. The system writes down exactly what it saw at the moment it decided, and the trainer reads that. The boundary is data, not code.

The watchdog sits on a different provider on purpose. Its entire job is to say "nothing has been recorded for eleven minutes" — and it cannot say that if it goes down with the thing it is watching.

What this costs, honestly

Four real costs, none of them "learn a new language." They are listed because the earlier research got the first one wrong in the optimistic direction, and a plan built on the optimistic version would have hit all four in week one.

01
The build step is gone, the checker is not
Node runs typed files directly — but it strips the types without checking them. You still install the checker and still run it in the background.
The upside is real: the developer is never blocked by it. He runs the file; the check reports later.
02
Four features crash at 3am instead of in the editor
A handful of older TypeScript features cannot be stripped, so using one fails when the code loads, not when it is written. In a system touching money that is the worst failure shape there is.
One line of config turns all four into editor errors. Not optional; goes in the first commit.
03
Import shortcuts do not work
The tidy path aliases most projects use are invisible to Node here. Imports have to be written a specific, slightly uglier way.
A layout decision forced by the runtime — so it belongs in the first commit, not the fortieth.
04
Two weeks of friction, then it stops
Strict settings generate hundreds of complaints on day one. Bounded and fixable by staging them.
The two noisiest stay off until the system runs. Types are mandatory only at the edges — ordinary function bodies are left alone.

One thing types explicitly do not buy: they vanish at runtime, so they prove nothing about the JSON a vendor actually sends. That is a separate, unavoidable piece of work — a checker per platform, run against recorded real responses, so a vendor changing shape fails the build. That cost is identical in every language, and believing otherwise is the most common way a team thinks it is protected when it is not.

The short version: the build is not wrong because JavaScript is sloppy. It is wrong because this design is made almost entirely of promises about shape, and the current language cannot hold one. The zero on the harbour clip is what that looks like in the product — not a crash, not an alert, just a quietly wrong answer to the one question the whole thing is asking.
