The claim's central thesis is correct and the July 22 spec's conclusion was genuinely wrong: a list endpoint returning 200 does exist, it is free, it needs no authentication, its rate limit is exactly 60/min per the server's own headers, and /coins/search really is 404. I confirmed every one of those literals directly. But the claim fails on two specifics that are load-bearing for anyone acting on it.

(1) The endpoint is named without a host, and the host is the entire question. "The pump.fun /coins endpoint" is 200 on exactly ONE of six hosts. The two most obvious/most-cited hosts — frontend-api.pump.fun and frontend-api-v2.pump.fun — return 530 and 503. An implementer handed this claim as written has a roughly 1-in-6 chance of hitting the working host. This is precisely the unqualified-endpoint-name failure mode that sank the prior pass, so I am not waiving it.

(2) "supplies mint, image_uri, created_timestamp AND the twitter source link in one call" is false as a general statement. The first three are universal: 50/50 present and non-empty. `twitter` is not. The key is absent from 14 of 50 records and empty in another, leaving 35/50 (70%) non-empty. Of those 35, only 32 are actual /status/<id> tweet permalinks; 3 are bare profile URLs (e.g. https://x.com/Lucaonsolana) with no originating tweet. So an actual usable "twitter source link" arrives for ~64% of newly created coins, and ~30% carry no twitter data at all. For an indexer whose purpose is resolving a coin to its source tweet, the claim's phrasing implies a guarantee that the data does not provide — the twitter enrichment path still has to exist for a third of coins.

One further caveat the claim omits entirely, which materially changes the build decision: this is an undocumented internal frontend API, not a public product. There is no official documentation (pump.fun/docs is a marketing page), and the response carries `access-control-allow-origin: https://pump.fun`, i.e. CORS is locked to pump.fun's own origin — so it is not browser-callable from the Insidor frontend and must be proxied server-side. The dead v1 and v2 hosts are direct evidence that pump.fun breaks these without notice. "No API, must build own index" was the wrong conclusion, but "there is a supported API to depend on" is also wrong; the correct read is that /coins is a useful unsupported shortcut that needs a fallback.
